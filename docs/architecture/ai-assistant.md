# Invekta AI

Existing message composer (`api/ai.py`, `AiAssistant.tsx`) now selects a single Groq chat-completions provider when explicitly enabled. Disabled mode preserves local templates and labels their limitations. An enabled provider without its separate `CRM_GROQ_API_KEY` returns 503, with no fallback or network request. Legacy OpenAI credentials are never reused. No new packages or lockfile changes are required. See README for exact environment setup, Free-plan caveat and owner-controlled Manus publication.

`ai_provider.py` posts only to `https://api.groq.com/openai/v1/chat/completions`, sends JSON instructions and validates nonempty bounded subject/body with extra fields forbidden. Truncation/refusal/invalid JSON is rejected. No tools, email sending, browsing, automatic retries or paid-provider fallback. The default Groq-hosted `openai/gpt-oss-120b` is listed in Groq's current Free limits (checked 2026-10-15); model availability and billing plan remain account settings. Client output is plain editable text, never executable HTML.

The composer submits just company_id/instructions. Mode, goal, tone and language default to auto; the provider derives them from the instruction (Serbian Latin/professional if unspecified). Prior explicit optional API fields remain supported for compatibility. Context contains the selected visible company, names/positions of its valid recipients, explicit user input and current brand knowledge. An explicit legacy contact_id narrows recipient resolution; matching opportunity selection remains supported through the API. It excludes other clients, other brands' knowledge and sales-document binaries. Contact email addresses are resolved by the CRM, not the model, and are not sent automatically; freeform input/signatures may contain personal data. Generation occurs only on explicit submit with a disclosure next to the form. No retention guarantees are implied for the provider.

Author/session/active membership/company visibility are checked before calling and again before returning content. The 20-attempt/15-minute per-user budget remains. The user-row lock reserves budget before releasing the transaction for the network call. Provider failures consume an attempt; missing configuration does not. Revoked access prevents returning generated content. `GET /ai/companies/{company_id}/recipients` authorizes the company and previews valid recipients. `ai_recipients.py` filters by company and business unit, validates historical addresses and deduplicates case-insensitively in stable contact-ID order. Empty addresses stay empty. `POST /ai/generate` refreshes recipients after the provider/access recheck and returns subject/body/recipient/recipients/model; it never creates or updates an AiDraft. Attempts contain actor/time, never user prompts or output text. The default UI has just the instruction textarea and searchable company field; it previews recipients read-only and allows editing To/subject/body after generation. Changing company clears previous output immediately, and canceled preview responses cannot fill another company. Clipboard includes To; a separate button copies only addresses. Admin knowledge remains behind a compact button. The browser keeps composition and generated edits in React state only, with no localStorage/sessionStorage/IndexedDB, history list or save button. Navigation/refresh starts empty. Existing database and browser drafts are left untouched; the legacy authenticated private GET remains read-only for compatibility, while old POST/PATCH return 410 after access checks. No schema change is needed for this removal.

`brand_knowledge.json` bundles short sourced public summaries from owner-supplied official websites, with source URLs/date. It is a starting knowledge base, not a complete catalog or live retrieval system. `brand_knowledge.py` uses bundled content only until an administrator saves an override; an explicit empty override remains empty. GET/startup performs no seed or writes. `api/ai_knowledge.py` lets enabled members read their brand knowledge and only brand admins/platform admins with membership update it. Payloads are bounded to 12,000 characters (fits MySQL TEXT with utf8mb4), versioned with row locks and conflict checks. Row-creation races return 409. Sources are facts rather than trusted instructions; model accuracy is still subject to human review.

Migration `c9d7a4e8f201` over `b8a6c2d1e409` adds a single table using portable types and foreign keys, without modifying existing records. Readiness checks the table publicly without needing AI configuration. Review/backup before applying on managed storage; all implementation-time DB work is restricted to isolated local PostgreSQL `_test`. Docker still bundles `/app/shared` and `/src/shared`, uses one port and existing locked dependencies.

Regression tests mock Groq transport and cover JSON protocol, rate/time/auth/provider errors, legacy-key isolation, brand scoping, shared knowledge permissions, stale writes and default/empty overrides. Browser tests exercise the actual FastAPI/PostgreSQL access with a mocked upstream response and assert no message persistence. A real Groq call/Serbian output quality must be confirmed after the owner's server key is configured. Never use production customer data for that initial check.

The provider identifies itself honestly as `InvektaCRM/0.4` with `Accept: application/json`; TLS and proxy settings are unchanged. `groq_errors.py` consumes/closes HTTP errors with an 8 KiB limit, distinguishes authentication, allowlisted organization/project model restrictions, recognizable edge responses and unclassified 403s. Raw bodies, headers, arbitrary codes and exception reasons never enter API details or diagnostic output. DNS/TLS success does not identify the source of a 403. `python -m app.check_ai_connection` uses the same generation client once with generic instructions only, without opening a DB/session or printing generated content. Its JSON contains only a status, predefined category, response format and allowlisted code; it stops before networking when disabled/unconfigured. Run it in the published runtime to confirm production access, not merely in preview. No schema or public route changes are involved.
